# Archived review — Production readiness review and evidence

Historical evidence for 7 October 2026 only. Current instructions: [operating guide](operations.md) and [Oracle runbook](../deploy/oracle/README.md). This document does not attest to the present runtime.

Reviewed 2026-10-07 across `smart-factory-iot`, `smart-factory-iot-backend` and `smart-factory-iot-edge`. The selected target is **Vercel frontend plus one immutable image deployed to separate Render web and worker services**. Existing dashboard accounts/roles remain authoritative; notifications use the in-app inbox and configured transactional email provider. Live DHT11 ingestion and a commissioned 200 ms WROVER indicator pulse were verified; no production deployment, physical arm movement or firmware flashing was performed.

## Assessment

The code now has a substantially stronger tested local release path. It is **not certified 100% production ready**. Automated OTA is absent, and deployment-specific cloud, hardware, capacity and recovery acceptance remains outstanding. The web role can be replicated on a paid Render plan, but the MQTT worker intentionally remains a singleton and is not highly available. Do not claim these gaps are covered by unit tests or a successful Docker build.

## Reproducible verification

Run these from the dashboard checkout with sibling repositories present:

```bash
pnpm check
pnpm build
E2E_PORT=3100 pnpm e2e
pnpm docs:check
pnpm audit --audit-level=moderate
python3 scripts/prepare-backend-context.py ../smart-factory-iot-backend /tmp/factory-backend-context
docker buildx build --load --build-context backend=/tmp/factory-backend-context -f deploy/render/Dockerfile -t smart-factory-render-review:local .
python3 scripts/bundle-smoke.py
python3 scripts/audit-container.py --output /tmp/factory-container-audit.json
pnpm e2e:system
```

The last command needs the local BaSyx stack and edge Python dependencies. Dashboard tests require explicit dedicated `TEST_DATABASE_URL`/`TEST_REDIS_URL`; `pnpm e2e` provisions them and never uses the developer's `.env.local` database. External Assistant calls are disabled in tests. Disposable outage-test PostgreSQL volumes preserve records across stops and are deleted after the run.

Backend: `dotnet test src/SmartFactory.sln -c Release` with the .NET 8 SDK/runtime. Edge: `python3 -m unittest discover -s raspberry-pi/tests -v` and `platformio run --project-dir esp32-wrover --environment compile-check`. The Arduino arm sketch was compiled separately. Firmware platform/libraries are pinned to the versions compiled during this review. Compilation is not evidence of a safe hardware update.

NuGet gate: `dotnet restore src/SmartFactory.sln -p:NuGetAudit=true -p:NuGetAuditMode=all -p:NuGetAuditLevel=high -warnaserror:NU1900,NU1903,NU1904 --force-evaluate`. The initial dependency tree contained `System.Net.Http` 4.3.0 from xUnit 2.5.3's legacy NETStandard dependency; xUnit 2.9.3 selects modern framework assets and removes that dependency. The initial combined image scan reported 129 high and 6 critical package/advisory matches. The reduced, updated runtime passed the six-process acceptance suite and a fresh Trivy scan with **zero high/critical findings**. No ignore list or unfixed-vulnerability exclusion was used. The scan is local with telemetry disabled; it downloads public advisory databases and does not export application data. [Trivy's documented telemetry controls](https://trivy.dev/docs/latest/advanced/telemetry/) describe the disabling option.

The gateway's full 20-package Python tree passed `python -m pip_audit -r raspberry-pi/requirements.txt --strict --progress-spinner off` after upgrading python-dotenv to 1.2.2. The [maintainer's advisory](https://github.com/theskumar/python-dotenv/security/advisories/GHSA-mf9w-mj56-hr94) covers unsafe symbolic-link handling during `.env.local` rewrites. Edge CI and the coordinated release use pinned pip-audit 2.10.1 and reject known vulnerabilities; this audit does not scan the physical Pi's OS image.

Verified locally: TypeScript check and production frontend build; **79 dashboard/API tests**; **92 .NET tests**; **42 gateway tests**; ESP32 and Arduino firmware compilation; repeated migrations; live role checks; anonymous private-route denial; durable/owner-scoped inbox and notification-worker restart; actual SQL gaps/null-safe aggregates; database and individual-service readiness failure/recovery. The real cross-repository smoke passed AAS provisioning and retained profile application, engineer command delivery to allowlisted simulated serial hardware, viewer denial, Pi-local sensor delivery through the durable queue and MQTT/.NET/PostgreSQL pipeline, named-signal availability in dashboard analytics, backend-outage replay without duplication, Assistant retrieval, and liveness/readiness behavior during database loss/recovery. SMTP configuration and recipient-policy tests do not send real email; Resend transport tests use a fake API key and HTTP handler.

The live local stack also showed `esp32-wrover-01` attributed to `pi-edge-01` as a healthy `DHT11`, publishing fresh temperature and humidity samples at approximately five-second intervals; the final inspected sample was **24.7 °C and 38% RH**, three seconds old. This proves the current gateway-to-dashboard path and device attribution, not sensor calibration accuracy. The registered arm uses asset ID `urn:smart-factory:asset:ada031-v4-arm-01`, protocol `ada031_v4_serial`, 9600 baud and stable path `/dev/serial/by-id/usb-1a86_USB2.0-Serial-if00-port0`. Its final gateway profile and edge code have not yet been installed on the physical Pi because an administrator credential was not available during this review; therefore live robot telemetry and physical UI actuation remain unverified.

The combined image acceptance suite and zero-high/critical container scan also passed for Render's **Linux AMD64** architecture, executed under local Docker emulation. The documentation check passed for **41 Markdown files, 123 local links and 11 rendered Mermaid diagrams**. All four CI/CD workflows passed Actionlint. The production frontend built 3,469 modules; its largest generated chunks were approximately 396 kB raw and 117 kB gzip. Measure browser performance under the actual plant network during acceptance.

Optional live AASX acceptance has also passed against local BaSyx. Vendor corpus and official conformance checks remain distinct acceptance requirements; no arbitrary AAS/AutomationML metamodel conformance is claimed.

## Outstanding release gates

1. **OTA is a missing feature.** The current ESP32 has no network firmware receiver, Pi has no dashboard-driven updater, and there is no signed compatible artifact/boot acknowledgment/rollback rollout. The UI correctly rejects deployment/rollback rather than inventing success. Existing USB flash and staged Pi installation instructions remain the supported update procedures. Implement and validate signed OTA on representative targets before advertising it.
2. **Cloud acceptance:** configure the documented GitHub production environment, actual Vercel/Render projects, GHCR access and managed-provider TLS/ACLs before merging the push trigger to the protected production branch. Disable independent Vercel and Render auto-deploy paths. Verify first-party cookie forwarding, logout, role denial, distinct customer/client IP attribution, representative AASX proxy uploads and migration/rollback on a restored staging database. The release workflow was reviewed and parsed locally; it has not been executed in the user's GitHub/cloud accounts.
3. **Email acceptance:** configure the Gmail app password in the Render worker and test a controlled signup and technician mailbox, provider throttling, and ambiguous retries. When migrating to Resend, verify the sender domain, API key and allowed recipient domains first. The inbox retains the correlation ID; provider acceptance still does not confirm mailbox delivery.
4. **OT commissioning:** install the reviewed edge bundle and retained arm profile on the physical Pi, then verify the stable USB identity, permissions, reconnect behavior, command expiration and no repeated motion after power loss. The first serial open may reset the Arduino and move it to its 90-degree startup pose, so commissioning requires a cleared workspace and direct supervision. Verify real sensor accuracy/units/scaling, device credentials/ACLs and OPC UA trusted certificates. ADA031 serial acceptance and reported target angles are not position/motion feedback; 90-degree neutral is not electrical off or an emergency stop. Application controls cannot replace machine safety functions.
5. **Capacity and availability:** measure throughput/queue depth, retention, database connections, API latency and six-process memory/CPU against expected factory loads. Render disk-based sequential deploys protect the stable MQTT identity and [introduce a short availability interruption](https://render.com/docs/disks). High availability/multi-instance ingestion needs a separate ownership design and tests.
6. **Backup/recovery and observability:** verify provider backups/restoration, recovery objectives, migration compatibility, production alerts, edge spool overflow handling and queue age monitoring. Logs/tests alone do not prove disaster recovery. Add full account/control audit retention where organizational policy requires it.
7. **Runtime and dependency lifecycle:** migrate .NET 8 and its supported dependencies before 2026-11-11 and repeat the full suite. [Microsoft lifecycle dates](https://learn.microsoft.com/en-us/lifecycle/products/microsoft-net-and-net-core) define the deadline. Node, all-transitive NuGet and the runtime-image high/critical audits passed during this review and are release gates; repeat them for each image. These do not certify installed Pi operating systems or ESP32/vendor firmware dependencies. Maintain their inventories and run platform-specific scans before commissioning.
8. **Product scope:** this deployment uses a single factory account/role domain. Public multi-tenant customer isolation is not implemented. Production grouping uses persisted asset metadata; the non-durable process-local device-group API was removed. Automated password recovery remains unavailable; administrator onboarding exists, but a verified user recovery/rotation workflow remains required. Historical downtime inferred by older migration 0010 needs operator reconciliation; the review does not rewrite historical factory records automatically.

See [the canonical deployment guide](../RENDER_DEPLOYMENT.md) for configuration, migrations, release order and rollback. This evidence is bounded to the tested source and local fixtures; plant acceptance must use the actual deployment and commissioned equipment.
