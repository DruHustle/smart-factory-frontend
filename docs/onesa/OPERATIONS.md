# Optional Onesa producer

This adapter is disabled by default. Smart Factory's native 3D, setup, files, history, auth and simulator are independent; see [equipment monitoring](../equipment-view.md). No deployed Onesa twin API was found. `urn:smart-factory:onesa-proposed:1.0.0` is an app-owned proposed transport, not an accepted Onesa contract. The separate `onesa-industrial-evidence-v1` synthetic JSON export validates against the inspected consumer model; it is not streaming ingestion.

## Configuration and setup

Apply dashboard migrations with `pnpm db:migrate`; deploy the companion backend provenance migration before using the new MQTT envelope. Keep credentials in existing server/edge secret stores. Set `ONESA_ENABLED=true`, a stable UUID `ONESA_INSTALLATION_ID`, approved `ONESA_WORKSPACE_ID`, exact `ONESA_INGESTION_URL`, exact `ONESA_APPROVED_ORIGIN`, the explicit proposed `ONESA_CONTRACT_ID`, and a least-privilege `ONESA_SERVICE_TOKEN`. HTTPS is mandatory except explicitly enabled nonproduction loopback fixtures. Redirects, URL credentials/query strings and browser-supplied destination scopes are prohibited. Shared demo-account deployments cannot enable private integration.

The first configuration persists installation, workspace and destination fingerprint. Changing those requires an explicit reviewed migration, not a payload override. Rotating a service secret does not change equipment IDs; restart with the new secret and use the administrator's retry/reconnect action. Do not place secrets in Vite variables or URLs. Private integration status, mappings, retries, exports and diagnostics require individual engineering/admin access; retries/resume require admin. Shared demo identities cannot access them.

Register source equipment with immutable UUIDs, external AAS identifier, serial/type, components and metric bindings. Preview and apply registration with its expected revision. Map every source component explicitly to one authorized target equipment/component. Two installed instances cannot share a target equipment mapping. Missing/ambiguous/retired sources remain visible; names never route measurements. Preview/apply changes use optimistic concurrency and audit records. Metadata previews are source-owned handoffs; no nonexistent consumer registration API is called. Consumer rules, annotations, history and user configuration are not overwritten or deleted. Twin deep links remain unavailable until a verified consumer route exists.

## Telemetry and delivery

The existing Pi relay → MQTT → .NET TelemetryService → Node pipeline is retained. The .NET durable bridge persists original optional provenance. The Node telemetry transaction captures an immutable source/mapping snapshot into PostgreSQL through a savepoint. No HTTP call occurs on acquisition. Normalization commits before network delivery, so a slow/offline receiver holds no acquisition capacity lock. Local monitoring continues if optional capture/delivery fails.

Source observation time, gateway receipt time and receiver ingestion time are separate. UTC is explicit. More than five minutes future skew is rejected; delayed/future-tolerance classifications remain distinct from quality. Original IDs/times survive retry. Unclassified legacy samples are quarantined for export rather than called live. Numeric values must be finite. Missing values remain absent; raw values/units and supported conversion factors are recorded; no aggregation is invented. Retained/delayed timestamps do not refresh on redelivery. Simulated and replay provenance, session/sequence/run IDs, source quality, source connection transitions and identifiable source alarms are preserved. Derived Onesa events cannot be fed back as source events.

Delivery is at least once. A successful TCP/HTTP response is not acknowledgment. Each expected event must have one matching scoped accepted/duplicate receipt with receiver-generated ingestion time; malformed/oversized/missing receipts retry. Batches are configurable 1–100 events (default 50). Partial receipts acknowledge only accepted items; rejected items quarantine; retry items retain their IDs. Requests time out after 10 seconds by default. Network, 408/425/429/5xx retry with bounded exponential jitter and Retry-After (one-hour cap). Other failures quarantine. 401/403 suspend delivery pending operator rotation/resume. Default maximum attempts: 12.

`ONESA_MAX_QUEUE_ROWS` defaults to 10,000 and caps captured/pending/quarantined/acknowledged storage; per-source payloads are already bounded to 16 KiB. Capacity may reclaim old acknowledged rows. If still full, new optional captures are discarded with a durable count. Acquisition continues. Default retention is 168 hours (maximum 720); expired unacknowledged rows increment the discard counter. Quarantine counts and delivery receipts are visible; authorized retry processes at most 100 records/action, preserving normalized mappings. Pending reconnect retries can be brought forward explicitly. Audit retention is 90 days. Receiver deduplication must outlive every supported retry/replay horizon. Exactly-once delivery is not claimed. A capture failure outside available adapter storage is logged and reported as process-local `captureFailures`; migrate before enabling the feature.

## Reproducible local MQTT walkthrough

All credentials below are isolated test values, never equipment/hosted credentials. The frontend producer and receiver tests need only this repository. This opt-in protocol walkthrough additionally uses the existing Smart Factory backend and edge repositories belonging to this application; it does not require an Onesa checkout.

1. Start `docker-compose.e2e.yml` with project `smart-factory-onesa-e2e`. Its loopback PostgreSQL/Redis ports are 55432/56379. Apply dashboard migrations.
2. Build the existing backend TelemetryService in Release/net10.0. Start `docker-compose.onesa.yml` combined with the e2e file: local Mosquitto 2.0.22, isolated telemetry DB and the existing subscriber on .NET 10. The subscriber forwards to the dashboard on port 3108 with test token `isolated-onesa-dashboard-bridge`.
3. Use a private local env file (outside Git) with the e2e database/Redis, a synthetic session secret, `PORT=3108`, `ENABLE_DEMO_ACCOUNTS=false`, and approved fixture scope: installation `53ded05b-c1aa-4faa-aa65-4747637baac0`, workspace `proposed-test-workspace`, proposed contract above, origin `http://127.0.0.1:18640`, URL ending `/proposed/v1/batches`, `ONESA_ALLOW_LOCAL_HTTP=true`, token `isolated-contract-test-token-only`. Set `ONESA_RECEIVER_DATABASE_URL` to the isolated test DB only.
4. Run `node --env-file=/path/to/private-test.env --import tsx scripts/onesa/seed-fixture.ts`, then the Node server and `scripts/onesa/run-receiver.ts` using that environment. The receiver is explicitly a proposed-contract fixture, not Onesa. It stores fixture receiver tables only in the isolated DB.
5. Run the edge virtualenv's Python on `scripts/onesa/scenario.py deterministic-pump-v1`. It uses the existing `forward_local_message` and `DurablePublisher`, publishing ten deterministic normal/threshold/recovery/disconnected/stale samples across two source instances over real MQTT. All remain simulated. Run `scripts/onesa/verify-walkthrough.ts` with the private test environment to require ten source samples, 38 acknowledged events, two instances and six mapped components. Repeating the same run deduplicates.
6. Stop only the fixture receiver. Repeat with run `outage-pump-v1`; `scripts/onesa/verify-outage.ts` requires ten persisted source samples, pending delivery and Error status while acquisition continues. Use local 3D/history/documents during the outage. Restart the receiver, rotate any rejected test credential if needed, and use the authorized retry/reconnect action. Confirm receipts/backlog recovery; source IDs and observation times must remain unchanged.

Unit/HTTP tests exercise duplicate/lost receipts, out-of-order data, replay separation, source alarms, scope isolation, outage, restart, limits, invalid credentials and mixed partial receipts. Real-equipment and actual Onesa twin/assistant/hosted verification remain pending.

AAS 3.0 JSON and AASX are serialized with pinned BaSyx Python SDK 2.0.1, independently verified with aas-core3.0 1.1.2 and round-tripped through BaSyx. They include two instances, component IDs, properties, explicit telemetry bindings, model revision/hash/provenance/coordinates and maintenance reference. Custom application submodels are labeled as such. IDTA 02026 informs 3D-file provision; template conformance is not claimed. AAS is not the telemetry transport. No Onesa AAS importer was found, so consumer acceptance is pending. Exports require individual engineering access and contain no industrial endpoints or credentials.
