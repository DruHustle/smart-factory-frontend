# Smart Factory review — 28 October 2026

The review includes the frontend/Express API, .NET companion services and Pi
gateway, including the graphical Assistant, shared design system and Service
health release. It preserves the Vercel → Oracle ARM64 API topology, one MQTT
worker, the existing BaSyx stack, and Smart Factory's independence from Onesa.

## Corrected findings

| Finding | Remediation and regression evidence |
| --- | --- |
| Event retention deleted notification history through a cascading foreign key. | Event expiry now clears only the event link. A disposable database regression verifies retained content, read actions and current administrator scope after demotion. |
| A queued private infrastructure email could reach an account demoted to engineer. | The actual delivery worker reloads the account and requires the current administrator role for infrastructure messages. PostgreSQL regressions queue as admin and deliver after a role change using a recording sender. |
| The feature release pinned a backend predating the Free-instance memory and idle-polling corrections. | Qualification includes those merged corrections and the delivery authorization fix. All companion identities remain full immutable revisions. |
| Readiness and schema checks did not require the exact qualified backend and edge sources. | Promotion compares both source identities with the qualification manifest and requires a fresh compatible singleton-worker receipt. |
| Post-deployment checks could pass while the public origin served an old UI artifact. | The release workflow verifies the public `release.json` revision, application, capability contract and timestamp, then checks the API through that same origin. Release identity is not cached. |
| The root deploy helper directed operators to the retired Render release. | It now points to Oracle API-first promotion and the gated Vercel workflow. |
| OTA history accepted negative, fractional or arbitrarily large limits. | API validation bounds history to 1–1,000 entries and positive integer device IDs, with tests proving invalid requests never reach storage. |
| New navigation and Assistant behavior disagreed with legacy browser assertions. | Journeys use the actual Sources & context action, verify authorized snapshot evidence and assert every administrator navigation group. |
| Screenshot paths assumed a macOS-only writable directory. | All new visual suites default to the portable CI artifact directory. |
| New infrastructure functionality lacked an operating guide. | The [Service health guide](service-health.md) explains access, evidence scope, collection, notifications, retention and recovery receipts. |
| Reusing the old production backend for rollback would lose the new access/pool safeguards, and its API rejects extended worker receipts. | An immutable compatible rollback pairs the previous UI/API with a backend retaining the new safeguards and the original receipt shape. ARM64 qualification tests rollback and roll-forward and retains both exact image archives. |

## Verification record

Local validation includes the production build, TypeScript check, non-database
frontend tests, 241 .NET non-PostgreSQL tests and all 78 Pi gateway tests. Database,
full browser, live broker, AAS, exact ARM64 image and restore checks run on the
isolated GitHub Actions infrastructure. Passing unit tests alone do not qualify
the release.

The feature requires migration `0030_infrastructure_monitor` and the Assistant
visuals/Service health capabilities. The production baseline observed during
review was frontend/API `a83a190`, backend `19a70a7`, schema `0029`, with a fresh
compatible worker. That baseline does not provide the new server features.
Promote the exact qualified Oracle API and singleton-worker image before the
new UI. Retain the tested rollback image and existing owner-only runtime
configuration. [PR 14](https://github.com/DruHustle/smart-factory-frontend/pull/14)
and [backend PR 9](https://github.com/DruHustle/smart-factory-backend/pull/9)
retain the current revision's CI evidence.

Physical-device commissioning, firmware flashing/OTA receiver implementation,
external Onesa acceptance and a verified production backup/restore remain
separate operating acceptance. Software acknowledgement is not physical
movement, email acceptance is not recipient delivery, and unavailable host or
provider measurements remain unknown.
